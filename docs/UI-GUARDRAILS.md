# خط‌مشی ارتقای رابط کاربری PersonalFinance

## خط مبنای تأییدشده

ظاهر فعلی مورد تأیید مالک است. مرجع دقیق آن در Git با تگ `ui-baseline-2026-11-07` و کامیت `83bcf8a` نگهداری می‌شود. این نسخه سقف طراحی نیست؛ کف کیفیت است. هر تغییر باید یک مشکل مشخص را بهتر کند و با شواهد نشان دهد که کیفیت افت نکرده است.

جهت بصری فعلی:

- رابط فارسی و راست‌به‌چپ با منوی ثابت در سمت راست
- فضای کاری تمام‌عرض در دسکتاپ، با فاصله‌گذاری کنترل‌شده و فرم‌های خوانا
- داشبورد مالی متراکم اما قابل اسکن، همراه با نمودار، مقایسه و نشانه‌های بصری
- پالت اصلی سبز عمیق با آبی و فیروزه‌ای خنک
- سه تم تاریک `evergreen`، `midnight` و `amethyst`، به‌علاوه حالت روشن
- فونت محلی Vazirmatn، آیکون‌های Lucide و ارقام جدولی برای مبالغ

## مواردی که باید حفظ شوند

1. ساختار ناوبری، مسیرهای اصلی، دسترسی سریع موبایل و جایگاه منوی راست.
2. تمام اطلاعات مالی موجود در کارت‌ها، نمودارها، جدول‌ها، فیلترها و حالت‌های جزئیات.
3. عرض کامل فضای کاری در نمایشگرهای بزرگ؛ محدودیت عرض فقط برای متن طولانی و فرم‌هایی که با کشیده‌شدن بدخوان می‌شوند.
4. سازگاری هر تغییر با همهٔ تم‌ها و رنگ‌های سفارشی ذخیره‌شدهٔ کاربر.
5. RTL واقعی با CSS منطقی، تاریخ شمسی، تومان، ارقام فارسی و ناحیه‌های LTR لازم.
6. دسترسی با صفحه‌کلید، focus واضح، هدف لمسی حداقل ۴۴ پیکسل و `prefers-reduced-motion`.

## موارد ممنوع

- بازطراحی سراسری بدون مسئله و هدف مشخص
- بازگرداندن قهوه‌ای، بژ، طلایی یا کهربایی به‌عنوان رنگ برند یا تزئین؛ زرد/قرمز فقط برای هشدار و خطای معنایی مجاز است
- حذف نمودار، مقایسه، جزئیات یا فیلتر برای خلوت‌تر نشان‌دادن صفحه
- رنگ‌های هاردکدشده در صفحه به‌جای توکن‌های معنایی
- اضافه‌کردن کتابخانهٔ آیکون دوم، فونت بیرونی یا CDN
- تغییر تم ذخیره‌شده یا رنگ سفارشی کاربر بدون مهاجرت دقیق
- تحویل UI صرفاً بر اساس کد، بدون مشاهدهٔ واقعی در مرورگر

## فرایند الزامی تغییر

### ۱. تعریف ارتقا

پیش از کدنویسی بنویسید: مشکل چیست، کدام صفحه درگیر است، کاربر بعد از تغییر چه چیزی را سریع‌تر یا روشن‌تر می‌فهمد و معیار موفقیت چیست. «مدرن‌تر شود» به‌تنهایی معیار قابل قبول نیست.

### ۲. ثبت خط مبنا

از مسیر درگیر با دادهٔ یکسان در عرض‌های ۳۷۵، ۷۶۸ و ۱۴۴۰ پیکسل تصویر بگیرید. برای صفحات اصلی، گزارش و تنظیمات، عرض ۱۹۲۰ پیکسل را نیز بررسی کنید. تصویرها باید حالت روشن و حداقل تم تاریک فعال را پوشش دهند؛ تغییر توکن یا تم باید هر سه تم تاریک را پوشش دهد.

### ۳. تغییر محدود

ابتدا از توکن‌های `frontend/src/app/finance.css` و `palettes.css`، سپس اجزای مشترک استفاده کنید. تغییر محلی را به بازنویسی سراسری تبدیل نکنید. اگر ساختار باید تغییر کند، دلیل و اثر آن بر مسیرهای دیگر را ثبت کنید.

### ۴. مقایسهٔ قبل و بعد

با همان داده، مسیر، اندازه و تم دوباره تصویر بگیرید و این موارد را مقایسه کنید:

| معیار | شرط پذیرش |
|---|---|
| سلسله‌مراتب | اقدام اصلی، عدد مهم و مسیر مطالعه روشن‌تر یا دست‌کم هم‌سطح قبل باشد |
| تراکم اطلاعات | اطلاعات مفید حذف یا پنهان نشده باشد |
| رنگ و کنتراست | WCAG AA و نقش معنایی رنگ‌ها حفظ شود |
| چیدمان | هم‌پوشانی، بریدگی و اسکرول افقی وجود نداشته باشد |
| تم‌ها | روشن، evergreen، midnight و amethyst سالم باشند |
| تعامل | hover، focus، disabled، loading، empty و error بررسی شوند |
| حرکت | هدفمند، کوتاه و در reduced-motion خاموش باشد |

### ۵. کنترل فنی

در پوشهٔ `frontend` اجرا شود:

```powershell
npm run typecheck
npm test
npm run build
```

برای تغییرات بزرگ، زمان جابه‌جایی بین صفحات، حجم بسته و تعداد درخواست‌های تکراری را نیز با نسخهٔ خط مبنا مقایسه کنید.

## تعریف «ارتقا»

تغییر زمانی ارتقا محسوب می‌شود که مسئلهٔ تعریف‌شده را حل کند، اطلاعات و قابلیت‌های موجود را حفظ کند، در اندازه‌ها و تم‌های هدف سالم باشد و شواهد قبل/بعد داشته باشد. سلیقهٔ متفاوت، ساده‌سازی بدون دلیل یا تعویض پالت به‌تنهایی ارتقا نیست.

## Git و بازگشت

- هر ارتقای UI در شاخهٔ جدا و با کامیت متمرکز انجام شود.
- توضیح کامیت یا سند همراه باید مسئله، نتیجه، تست‌ها و مسیرهای بررسی‌شده را ذکر کند.
- اگر نتیجه از خط مبنا ضعیف‌تر بود، تغییر UI همان کامیت باید قابل بازگشت باشد.
- شاخهٔ `codex/finance-foundation` برای منطق مالی و دیتابیس است. پیش از تغییر UI در آن، ظاهر را با تگ خط مبنا مقایسه کنید و تغییرات UI را انتخابی منتقل کنید؛ منطق مالی نباید بهانه‌ای برای بازطراحی ناخواسته باشد.
